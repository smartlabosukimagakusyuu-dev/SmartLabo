## 2. 利用可能ルート／利用不可ルート

### 許可リスト（`AppLayout.jsx`）

```js
const CONTRACT_ALLOWED_PATHS = ['/', '/settings']
```

**拒否リストではなく許可リストにした。**
拒否リストだと、あとから画面を足したときに止め忘れて業務機能が
素通りしてしまう。許可リストなら足し忘れは「使えない」側に倒れる。

判定は**パスの完全一致**（前方一致にしない）。

| 契約が有効でなくても使える | 使えない |
|---|---|
| `/`（契約のご案内） | 業務画面すべて（`/customers`・`/tasks`・`/records`・`/manuals`・`/assistant`・`/brain`・`/documents`・`/search`・`/usage`・`/storage`・`/files`・`/dashboard`・`/schedule`・`/admin/*`） |
| `/settings`（契約・ライセンス含む） | |
| `/billing/complete`・`/billing/cancelled`（レイアウト外） | |
| `/login`・`/password`（レイアウト外） | |
| ログアウト | |

### 実測

```
/customers へ直接アクセス → 現在のURL: /  見出し: ご契約状況
/settings  へ直接アクセス → 現在のURL: /settings  設定が開けた: true
```

戻す先の `/` が許可リストに入っているため、行き来を繰り返さない
（無限リダイレクトなし）。

## 3. 直接URL対策とサーバー側の制御

画面側の出し分けは**利便性のため**であり、実際の制限はサーバーが行う。
本工程でサーバー側の制御を緩めていないことを実測で確認した。

| 契約状態 | `GET /api/customers` |
|---|---|
| `active` | 200 |
| `payment_required` | 402 `PAYMENT_REQUIRED` |
| `past_due` | 402 `PAYMENT_PAST_DUE` |
| `canceled` | 403 `CONTRACT_CANCELED` |
| 知らない値 | 403 `CONTRACT_INACTIVE` |

### サーバー側の是正（1件）

知らない契約状態のとき、`checkContractAccess` が**共通経路まで塞いでいた**。
その会社の利用者はログアウトも、自分の情報の確認も、契約状況の確認も
できず、何もできない状態になっていた。

業務機能は引き続き閉じたまま、**出口と状態の確認だけを通す**ように直した。

```
修正前: 知らない状態 → すべて403（ログアウトもできない）
修正後: 知らない状態 → 業務機能は403、ログアウト・自分の情報・
                       契約状況・パスワード変更は通す
```

## 4. 読み込み中の安全性

`ContractContext` で次の4つを区別する。

| 状態 | 意味 | 業務機能 |
|---|---|---|
| `idle` | 未ログインなど、取得する必要がない | 開けない |
| `loading` | 取得中 | 開けない |
| `ready` | 取得できた | `active` のときだけ開ける |
| `error` | 取得に失敗した | 開けない |

- **`isActive` は `ready` かつ `active` のときだけ true**
- 取得前の既定値を `active` にしていない
- 取得に失敗したら契約情報を持ち越さない（前の値を残さない）
- 取得できるまでメニューも業務画面も描画しないため、
  一瞬だけ業務メニューが見えることがない
- 問い合わせは Context の1か所だけ。決済結果画面・設定画面は
  Context の値を使う（画面ごとに何度も呼ばない）

顧客画面に「Company OS」は出していない。
