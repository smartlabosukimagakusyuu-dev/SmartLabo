## 1. 採用した画面URL

| 画面 | URL | 配置 |
|---|---|---|
| 決済完了 | `/billing/complete` | ログイン後の単独画面（`/password`・`/setup` と同じ扱い） |
| 決済キャンセル | `/billing/cancelled` | 同上 |
| 契約状況 | **`/settings`（「契約・ライセンス」セクション）** | 既存の設定画面へ追加 |

### 契約状況画面に `/settings/billing` を採用しなかった理由

指示の候補は `/settings/billing` だったが、**既存ルーティング規則を優先した**。

Liteの設定画面は `/settings` の1ルートで、画面内のタブ（`section` の状態）で
「プロフィール／パスワード／会社情報／**契約・ライセンス**／初回セットアップ」を
切り替える作りになっている。既に「契約・ライセンス」セクションが存在し、
契約ライセンス数・利用中の社員・残り登録可能数を表示していた。

ここへ新しいURLを足すと、設定画面の入口が2つになり、
どちらが正しいのか分からなくなる。既存セクションを拡張する方が自然と判断した。

## 2. 契約状態別の表示

### `/billing/complete`

**URLへ到達したことを「支払い成功」の根拠にしない。**
必ずサーバーへ現在の契約状態を問い合わせ、その結果だけで表示を決める。

| 契約状態 | 見出し | 表示・操作 |
|---|---|---|
| `active` | お支払いが完了しました | 契約状態／契約人数／利用人数／残り登録可能人数／利用開始日<br>「利用を開始する」「メンバーを登録する」 |
| `payment_required` | お支払い状況を確認しています | 「反映まで少し時間がかかる場合があります。」<br>**回数を決めた自動再確認**（最大5回・3秒間隔）<br>「状態を再確認する」「契約状況の画面へ戻る」 |
| `past_due` | お支払いの確認が必要です | 業務を開始できるように見せない。支払い手続きの導線のみ |
| `canceled` | この契約は終了しています | 問い合わせの案内のみ |
| 未認証 | ログインが必要です | ログイン画面へ誘導（URLへ認証情報・契約情報を載せない） |

- **無限ポーリングにしない**（上限回数に達したら自動確認を止める）
- 画面の読み込みで**自動的にCheckoutを作らない**
- 時間切れでも「失敗」と断定しない

### `/billing/cancelled`

| 契約状態 | 表示 |
|---|---|
| `payment_required` | 「お支払いは完了していません」「ご契約は開始されていません。料金は請求されていません。」<br>**このときだけ**「お支払い手続きへ戻る」を表示 |
| `active` | 「ご契約はすでに有効です」。**再決済ボタンは出さない** |
| その他 | 状況を表示し、契約状況の画面へ戻る導線のみ |

- 画面を開くだけでDBの契約状態を変えない（読み取りAPIしか呼ばない）
- 自動でのCheckout作成・自動リダイレクトによる決済開始はしない
- ブラウザの戻る・再読み込みでも二重作成しない（押したときだけ作成）

### `/settings`（契約・ライセンス）

- ご契約状態（バッジ＋文言。色だけで伝えない）
- ご利用開始日
- 契約ライセンス／利用中の社員／残り登録可能数
- 管理者・一般利用者の内訳（既存表示を維持）
- ご利用料金（税別）
  - 基本料金 20,000円／月（管理者1名を含む）
  - 追加アカウント 3,000円／月・1名
  - **現在の月額見込み**
  - 初期設定費 10,000円
- 「初回のお支払いは、ご利用開始日によって日割りになる場合があります」
- 支払いが必要な状態のときだけ「お支払いのお手続きへ進む」（**管理者のみ**）

## 3. 契約状況API

### 新設していない（既存APIの拡張のみ）

`GET /api/contract/status`（WEB-SALES-2で新設済み）に、人数の情報を追加した。
`GET /api/me` の既存 license 情報と合わせて必要な項目がすべて揃うため、
**新しいAPIは作っていない**。

### 返却項目

| 項目 | 内容 |
|---|---|
| `contractStatus` | active / payment_required / past_due / canceled |
| `contractStartedAt` | 契約開始日 |
| `licenseCount` | 契約人数 |
| `activeUsers` | 現在の利用人数（停止中は含めない） |
| `seatsUsed` | 契約枠の使用数（**停止中も含む**） |
| `remainingSeats` | 残りの登録可能人数（契約数未設定なら `null`） |
| `quote` | 基本料金・追加席数・追加分・月額合計・初期設定費・税別・`firstChargeAmount: null` |
| `currentPeriodEnd` | 次回の請求期間の終わり |
| `nextAction` / `businessFeaturesAvailable` | 画面の出し分け用 |
| `canStartCheckout` / `canManageBilling` | 権限とStripe設定を含めた可否 |

`remainingSeats` は **seat制御（WEB-SALES-1B）と同じ数え方**にしている。
画面の「残り登録可能人数」と、実際に登録できる人数を一致させるため。

### 返却していないもの（テストで機械確認）

`stripe_customer_id` ／ `stripe_subscription_id` ／ Price ID ／
Stripe secret ／ Webhook secret ／ 認証トークン ／ 他社の情報 ／
メールアドレス一覧 ／ パスワードハッシュ

### 安全性

- 未認証は 401
- 会社IDは**セッションからのみ**取得。クエリ・本文の会社IDは読まない
  （`?companyId=` を付けても自社の情報しか返らないことを確認）
- 一般利用者も自社の状態は確認できるが、`canManageBilling=false` を返し
  決済の導線を出さない
- 支払い待ち・支払い失敗・解約中でも使える（契約状態の許可リストに含む）

## 4. 権限制御

| 操作 | 会社管理者・運営者 | 一般利用者 |
|---|---|---|
| 契約状況の確認 | ○ | ○（変更操作は出さない） |
| 決済の開始 | ○ | **×（403）** |
| 契約人数の変更 | ×（未実装） | × |
| Stripeの操作 | ×（画面から直接は行わない） | × |

- 画面の出し分けは `canManageBilling` / `canStartCheckout` に従う
- **サーバー側でも** `POST /api/billing/checkout` が管理者以外を403で拒否する
- 顧客向け画面に「Company OS」という名称は出していない（テストで確認）

## 5. 二重決済の防止

| 仕組み | 内容 |
|---|---|
| 自動作成をしない | 画面の読み込み・リダイレクトでCheckoutを作らない。押したときだけ |
| 連打の防止 | 処理中はボタンを無効化し、成功したらそのまま遷移する |
| 状態の制限 | `payment_required` 以外は 409 `CONTRACT_NOT_PAYABLE` |
| 冪等キー | 会社ID＋契約人数から作る固定値のため、連打しても同じCheckoutになる |
| キャンセル画面 | 支払い待ちのときだけ再手続きの導線を出す |

テストで「3回同時に押しても送信内容が同一」であることを確認した。
