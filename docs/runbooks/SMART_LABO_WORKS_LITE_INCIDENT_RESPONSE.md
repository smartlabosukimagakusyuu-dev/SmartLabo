# Smart Labo Works Lite 漏えい等対応 運用手順書

**版**：1.0.0（2026-08-11 作成 / WEB-SALES-8L）
**対象**：Smart Labo Works Lite および公開Websiteに関する、個人データの漏えい・滅失・毀損、
不正アクセス、その他の情報セキュリティ事故（以下「インシデント」）
**位置づけ**：プライバシーポリシー12項「漏えい等が発生した場合の対応」の対外的な約束を、
実行できる手順として定める社内文書。**本手順書に秘密値・本番コマンドは記載しない。**

---

## 0. 原則

- **止血を最優先**する。原因の特定より先に、被害の拡大を止める。
- **記録を取りながら動く**。時刻・事象・操作・判断を、対応と並行して記録する。
- **1人で抱えない**。検知した者は直ちに代表（または代表が指定した責任者）へ連絡する。
- 判断に迷う事項（報告義務の該当性等）は、**外部の専門家へ相談する前提**で保留にし、
  推測で「報告不要」と結論づけない。

## 1. 検知

インシデントに気づく主な経路：

- 利用者・契約者からの申告（お問い合わせフォーム・電話）
- 監査ログ（`audit_logs`）・ログイン試行記録・サーバーログの異常
- 外部事業者（Stripe・OpenAI・Google・レンタルサーバー等）からの通知
- 公開情報（SNS・掲示板等）での指摘

検知した者は、**気づいた時刻・気づいた内容・根拠**を記録し、直ちに次章の連絡を行う。

## 2. 初動連絡

1. 代表取締役（または代表が指定した責任者）へ、判明している範囲で第一報を入れる。
   未確定でも構わない。**第一報は30分以内**を目安とする。
2. 第一報に含める内容：何が起きたか／いつ気づいたか／影響し得る範囲（会社数・データ種別）／
   現在も進行中か。
3. 以後の対応の指揮者（責任者）を決める。以降の判断・広報は責任者へ一本化する。

## 3. 封じ込め

被害の拡大を止める措置を、影響の小さい順に検討・実施する：

- 該当利用者・該当会社のセッション破棄（休止・停止操作でセッションは即時失効する）
- 漏えいに使われた疑いのある認証情報の無効化（パスワードリセットの案内）
- 該当APIキー・シークレットのローテーション（Stripe・OpenAI・Google・SMTP。
  各事業者の管理画面から実施。値は本手順書にも記録にも書かない）
- 該当機能の一時停止（AI機能は `AI_ENABLED`、OCRは `DOCBOX_OCR_ENABLED`、
  メールは `MAIL_TRANSPORT` の設定で個別に止められる）
- 最終手段としてのサービス全体の一時停止

**証拠を消す封じ込めをしない**（次章）。サーバーの初期化・ログの削除・DBの上書きは行わない。

## 4. 証拠保全

- 対応を始める前に、可能な範囲でDB・ログ・設定のバックアップ（スナップショット）を取得する
- 監査ログ・ログイン試行記録・Stripeイベント台帳は追記専用・自動削除の対象外であり、
  そのまま保全される（消さない）
- 取得したバックアップの日時・保管場所・取得者を記録する
- 攻撃の痕跡（不審なリクエスト・アクセス元の傾向）は、原文のまま安全な場所へ写す

## 5. 影響調査

次を特定する（判明した範囲で記録し、随時更新する）：

| 調査項目 | 確認手段の例 |
| --- | --- |
| 影響を受けた会社・利用者の範囲 | 監査ログ・セッション記録・DBの該当行 |
| 漏えいし得たデータの種別 | 顧客情報／業務データ／アカウント情報／契約・請求情報の別 |
| 期間 | 最初の不審な操作〜封じ込め完了まで |
| 経路 | 認証突破／権限誤り／設定不備／委託先起因 等 |
| 進行中か終了か | 封じ込め後の監視で再発が無いこと |

- 要配慮個人情報・クレジットカード番号は、製品仕様上、当社DBに保存されない
  （入力禁止・Stripeが直接取得）。ただし利用者が誤って入力した可能性は調査で確認する。

## 6. 個人情報保護委員会への報告・本人への通知の判断

- 個人データの漏えい等が発生し、個人の権利利益を害するおそれが大きい場合、
  個人情報保護法に基づき、**個人情報保護委員会への報告**および**本人への通知**が必要になる。
- 該当性の判断（報告対象の類型・報告期限）は、事案の概要を整理したうえで、
  **外部の専門家（弁護士等）へ確認して行う**。自社判断で「不要」と結論づけない。
- 報告・通知を行う場合の内容は、影響調査（5章）の記録に基づき作成する。
- 契約者（会社）への連絡は、本人通知とは別に、判明した事実・影響範囲・当社の対応を
  誠実に伝える。**確定していないことは確定したと書かない。**

## 7. 外部事業者への連絡

事案の内容に応じて、関係する外部事業者へ連絡・相談する：

| 事業者 | 連絡する場合の例 |
| --- | --- |
| Stripe | 決済関連の不正・アカウント侵害の疑い |
| OpenAI / Google | APIキーの漏えい・不正利用の疑い（キーの無効化・利用履歴の確認） |
| レンタルサーバー／VPS事業者 | サーバー侵害・メール送信基盤の不正利用の疑い |

連絡した日時・相手・内容を記録する。

## 8. 復旧

1. 原因への対処（脆弱性の修正・設定の是正・認証情報の再発行）が完了していることを確認する
2. バックアップからの復元が必要な場合は、復元範囲・復元時点を責任者が承認してから行う
3. 復旧後、一定期間（目安1週間）は監査ログ・ログイン試行を通常より高頻度で確認する
4. 停止した機能の再開は、原因対処の確認後に責任者の承認を得て行う

## 9. 再発防止

- 事案の時系列・原因・対応・影響を振り返り、再発防止策を文書化する
- 製品側の対策（検証・制限・監査の追加）は、通常の開発工程（レビュー・テスト）に載せる
- 本手順書自体の不備が見つかった場合は、改訂履歴を付けて更新する

## 10. 実施記録

インシデント1件につき、次を記録して保管する（保管期間：7年を目安）：

| 項目 | 内容 |
| --- | --- |
| 検知日時・検知経路 | |
| 第一報の日時・報告者・責任者 | |
| 事象の概要・影響範囲（会社数・データ種別） | |
| 封じ込めの内容と日時 | |
| 証拠保全の内容（バックアップの日時・保管場所） | |
| PPC報告・本人通知の要否判断と根拠（専門家確認の記録を含む） | |
| 外部事業者への連絡記録 | |

| 再発防止策 | |

> 実施記録には認証情報・APIキー・パスワード等の秘密値を書かない。
> 個人データそのもの（漏えいした内容の写し）も、必要最小限の範囲を超えて転記しない。
