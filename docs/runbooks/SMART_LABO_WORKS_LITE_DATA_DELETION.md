# Smart Labo Works Lite 契約者データ削除 運用手順書

**版**：1.0.0（2026-08-11 作成 / WEB-SALES-8F）
**対象**：Smart Labo Works Lite の解約後データ削除、および契約者からの削除依頼
**位置づけ**：**承認付きの手動運用手順**。自動削除は実装していない。

---

## 0. この手順書がある理由

利用規約 第14条およびプライバシーポリシー 9項で、当社は次を約束している。

- 解約後90日間は契約者データを保持する
- 90日の経過後は、法令等により保存が必要な記録を除き、**当社所定の手順により削除する**
- 契約者からの削除依頼には、本人確認・権限確認のうえ30日以内を目安に対応する

WEB-SALES-8R の独立監査で、**この約束を実行する手段が製品にも運用にも存在しない**ことが
指摘された（監査 M2）。製品は論理削除（`deleted_at`）しか持たず、物理削除の仕組みがない。
そのままでは「削除の対象とする」と書きながら事実上の無期限保持になる。

本手順書は、販売開始時点で実行できる**手動の削除手順**を定めるものである。

> **自動削除は実装しない。** 期間の経過だけでデータが消えることはない。
> 削除は必ず、責任者の承認を経た本手順の実行によって行う。

---

## 1. 適用範囲

### 1-1. 対象となる契約

| 区分 | 起点 | 実行時期 |
| --- | --- | --- |
| 解約後の削除 | `companies.canceled_at`（解約確定日時） | 起点から**90日経過後** |
| 削除依頼 | 契約者からの依頼受付日 | 本人確認・権限確認の完了後、**30日以内を目安** |

### 1-2. 対象外（実行してはならないもの）

- `canceled_at` から90日を経過していない契約
- 契約状態が `canceled` 以外の会社（`active` / `past_due` / `payment_required`）
- 再契約の申し出を受けている契約（保留とし、判断を仰ぐ）
- 係争中・調査中の契約

---

## 2. 削除するもの／削除しないもの

**顧客業務データと、保存義務のある記録を明確に区別する。**
この区別を誤ると、法令上の保存義務違反、または同意の証拠の喪失につながる。

### 2-1. 削除する（顧客業務データ）

| 区分 | 対象 |
| --- | --- |
| 顧客・取引先 | `customers` |
| 記録・商談 | `records` |
| 予定 | `schedules` |
| タスク | `tasks` |
| 資料ボックス | `doc_box_items`、およびその抽出テキスト・OCR結果 |
| マニュアル | `manuals`、`manual_contents` 等の本文 |
| 文書ドラフト | `document_drafts` |
| 添付ファイル | `files` テーブルの行、および `UPLOAD_DIR` 配下の実ファイル |
| AI関連 | `ai_usage_logs`、`ocr_usage_daily`（利用量の集計。個社の業務内容は含まない） |
| セッション | `sessions`（対象会社の利用者のもの） |
| 利用者のPII | `users` の `name` / `email`（**行は残し、匿名化する**。下記2-3参照） |

### 2-2. 削除しない（保存義務・証拠として必要な記録）

| 区分 | 対象 | 理由 |
| --- | --- | --- |
| 同意の証拠 | `consent_records` | 利用規約その他の条件へ同意した事実を証する記録。規約14条4項で保持を明記 |
| 法務文書の版 | `legal_document_archive` | 同意記録が指す当時の本文。追記専用（DBのtriggerでUPDATE/DELETE禁止） |
| 決済イベント | `stripe_events` 等のイベント台帳 | 二重処理防止と請求の追跡。金額・課税の裏づけ |
| 契約・請求 | `companies` の契約状態・契約期間・`canceled_at`、`seat_change_requests` | 税務・会計 |
| 監査記録 | `audit_logs` | 不正防止・紛争対応 |
| ログイン試行 | `login_attempts` | 24時間で自動削除される（対応不要） |

### 2-3. 会社行・利用者行の扱い

**`companies` の行、`users` の行を単純に物理削除してはならない。**

理由：

1. `consent_records` は `company_id` / `user_id` に外部キー制約（`ON DELETE` 未指定＝
   `NO ACTION`）を持つ。同意記録が1件でもあれば、会社行・利用者行の削除は
   **FK違反で必ず失敗する**（migration 025 で確認済み）。
2. 会社行・利用者行を消すと、保存義務のある同意記録・監査記録が「誰の」ものか
   辿れなくなり、証拠としての価値を失う。

したがって：

- `companies` の行は**残す**。業務データだけを削除し、契約状態は `canceled` のまま保つ
- `users` の行は**残し、PIIを匿名化する**
  - `name` → `削除済み利用者`
  - `email` → `deleted-<users.id>@invalid`（一意性を保つため id を含める）
  - `password_hash` → ログイン不能な固定値へ置換
  - `status` → `suspended`
- 会社名（`companies.company_name`）は請求・税務記録との対応に必要なため残す

## 3. 実行前の準備

### 3-1. 対象会社の特定

1. 契約状態が `canceled` で、`canceled_at` から90日以上経過した会社を抽出する
2. 抽出結果を一覧にし、**会社ID・会社名・解約確定日・経過日数**を記録する
3. 再契約の申し出・係争・調査の有無を営業／サポート側へ確認する

### 3-2. 承認

- **代表取締役、または代表が指定した責任者の承認を必ず得る**
- 承認は書面またはメールで残す（承認者・承認日時・対象会社ID）
- 承認のない削除は**実行してはならない**

### 3-3. バックアップ

1. 本番DBの完全バックアップを取得する
2. `UPLOAD_DIR` 配下の添付ファイルのバックアップを取得する
3. バックアップの取得日時・保管場所・保管期限を記録する
4. **バックアップの復元可否を確認してから**削除へ進む

> バックアップの保管期間は、削除実行から最低30日とする。
> 誤削除の申し出があった場合の復旧余地を残すためである。

## 4. 実行手順

> **本手順書に本番コマンドは記載しない。**
> 実行は、承認を得た担当者が本番作業手順（別途管理）に従って行う。
> ここでは順序と確認内容だけを定める。

### 4-1. 削除の順序（外部キーの依存に従う）

子から親へ向かって削除する。逆順にすると外部キー違反で失敗する。

1. AI・OCRの利用ログ、セッション
2. 資料ボックスの抽出テキスト・OCR結果 → 資料ボックス本体
3. マニュアル本文 → マニュアル
4. 文書ドラフト
5. 記録・予定・タスク
6. 顧客・取引先
7. 添付ファイル（DBの行 → 実ファイルの順。逆にすると孤児ファイルが残る）
8. 利用者のPII匿名化（**行の削除ではない**）

各段階で、**対象会社ID以外の行に触れていないこと**を件数で確認する。

### 4-2. 実行中の確認

- 1段階ごとに影響件数を記録する（想定件数と一致するか）
- 他社のデータが1件でも含まれていれば**直ちに中止し、ロールバックする**
- 削除は1社ずつ行う。複数社を一括で処理しない

### 4-3. 実行後の確認

| 確認項目 | 期待 |
| --- | --- |
| `PRAGMA integrity_check` | `ok` |
| `PRAGMA foreign_key_check` | 0件 |
| 対象会社の業務データ件数 | 0件 |
| **他社の業務データ件数** | **削除前と同一** |
| `consent_records` の対象会社分 | **削除前と同一件数（残っていること）** |
| `legal_document_archive` | **削除前と同一件数（残っていること）** |
| `audit_logs` の対象会社分 | 残っていること |
| `companies` の対象会社行 | 残っていること（`contract_status = 'canceled'`） |
| `users` の対象会社行 | 残っており、氏名・メールが匿名化されていること |
| 添付ファイルの実体 | `UPLOAD_DIR` 配下から消えていること |
| アプリの起動 | 正常に起動すること |

### 4-4. 復元不能であることの確認

- 削除後、対象会社の業務データがアプリ上から参照できないことを確認する
- **論理削除（`deleted_at`）ではなく行が消えていること**を確認する
  （論理削除のままでは「削除した」と言えない）

---

## 5. 中止条件

次のいずれかに該当した場合、**直ちに中止し、ロールバックする**。

- 他社のデータが対象に含まれていた
- バックアップが取得できていない、または復元できない
- `foreign_key_check` に違反が出た
- 削除対象外（`consent_records` / `audit_logs` / `legal_document_archive`）に影響が出た
- 対象会社が再契約を申し出ていることが判明した
- 承認の範囲を超える会社が含まれていた

中止した場合は、事象・時刻・影響範囲を記録し、責任者へ報告する。

## 6. 実施記録

削除1件につき、次を記録して保管する（保管期間：7年を目安）。

| 項目 | 内容 |
| --- | --- |
| 対象会社ID | |
| 解約確定日 / 経過日数 | |
| 承認者 / 承認日時 | |
| バックアップ取得日時 / 保管場所 / 保管期限 | |
| 実施者 / 実施日時 | |
| 削除件数（テーブル別） | |
| 実行後確認の結果（4-3の各項目） | |
| 特記事項（中止・再実行など） | |

> 実施記録には**契約者の氏名・メールアドレス・業務内容を書かない**。
> 会社IDと件数で足りる。

---

## 7. 削除依頼への対応（規約14条5項・プライバシーポリシー11項）

1. お問い合わせフォームで依頼を受け付ける
2. **依頼者の本人確認**と、その会社を代表する**権限の確認**を行う
3. 削除範囲を確認する（会社全体か、特定の個人データか）
4. 保存義務のある記録は削除できない旨を、理由とともに回答する
5. 責任者の承認を得て、第3〜6章の手順で実施する
6. 完了後、依頼者へ対応内容を回答する（目安30日以内）

---

## 8. 本手順書の限界（明示しておくこと）

- **自動削除は実装していない。** 期間の経過だけではデータは消えない
- 本手順は**人手による運用**であり、実施漏れが起こりうる。
  月次で対象会社の有無を確認する運用を別途定めること
- 将来、自動削除を実装する場合は、本手順書の2章（削除する／しないの区別）を
  そのまま仕様とし、承認と実施記録の仕組みを併せて設計すること
- Stripe 側に保持されるデータ（顧客・請求書・支払い履歴）は本手順の対象外である。
  Stripe のデータ保持方針に従う。当社DBからStripeの識別子を消しても、
  Stripe側の記録は消えない点に注意する
