## 2. 追加する機能（第一段階の完成形）

```text
顧客情報 → 条件抽出 → 対象顧客を確認 → AIがメッセージ案を作成 → スタッフが確認・編集
→ スタッフが明示的にLINE送信 → お客様のLINEへ届く → 予約ページへ → WEB予約 → Salon側の予約へ反映 → 再来店
```

| # | 機能 | 内容 | 境界 |
|---|---|---|---|
| 1 | LINE公式アカウント連携 | 店舗の LINE Official Account を Salon テナントに紐付け（チャネル設定は店舗ごと・秘密値はサーバー側暗号化保管） | 店舗1アカウント |
| 2 | 顧客とLINEユーザーの安全な紐付け | 友だち追加→アカウント連携（LINEログイン or 連携トークン）で `line_user_id` を取得し、**店舗スタッフが顧客カルテと突合して確認**してから紐付け（自動統合しない＝電話・氏名での自動一致禁止の既存原則を踏襲） | 人が確認 |
| 3 | 条件抽出 | §4 の条件で対象一覧を作る（事実のみ） | Standard境界内 |
| 4 | 対象者一覧の確認 | スタッフが一覧を見て、送る相手を**個別に選ぶ／外す** | 人が確認 |
| 5 | AI文案 | 既存のAI投稿案と同じ設計（fake/openai Provider・氏名等はAIへ送らない・提案は保存しない） | 店舗が確認してから |
| 6 | 確認・編集 | スタッフが本文を確認・修正。**未確認の文案は送れない** | 人が決める |
| 7 | 明示送信 | 送信ボタンを押した人・時刻・対象・本文を **送信ログ**に記録。1回の送信上限と確認ダイアログ | 誤送信防止 |
| 8 | 配信 | LINE Messaging API（プッシュ／マルチキャスト）で送信。失敗・ブロック・未連携は結果として記録 | 送信責任 |
| 9 | 予約導線 | 本文に店舗ページの予約URL（既存 `/s/<slug>`）を含める。**AI対話予約・AI受付はしない** | 24時間WEB予約受付 |
| 10 | 反映 | WEB予約 → 既存の reservations へ。送信→予約の**件数**を記録（売上・LTVは扱わない） | Standard境界 |

## 3. 顧客フロー（お客様側・店舗側）

- お客様: 店舗ページの「LINEで友だち追加」→ 連携案内 → （同意のうえ）連携 → 店舗からのメッセージ受信 → 予約URL → WEB予約
- 店舗: 顧客カルテで連携状態を確認 → 「再来店のご案内」画面で条件抽出 → 対象確認 → AI文案 → 編集 → 送信 → 結果確認（届いた／ブロック／未連携）

## 4. 条件抽出（P33-LINE 設計候補・現schemaで取得可能なもの）

| 条件 | 取得元 | 備考 |
|---|---|---|
| 最終来店日（N日以上ご来店なし） | `visits.completed_at` | 既存 `revisitService`（60日）の拡張。**日数は設定値**・予測にしない |
| 来店回数 | `visits` の件数 | 事実の件数 |
| 利用メニュー | `visits.menu_id` → `menus` | 例: カラー利用あり |
| 担当スタッフ | `visits.staff_id` → `staff` | 例: 佐藤担当 |
| 未来予約の有無 | `reservations.start_at > now AND status='reserved'` | 予約済みの人へは送らない |
| LINE連携状態 | `customers.line_linked`（現状は手動）→ 実装後は `line_user_id` の有無 | 未連携者は対象外（送れない） |
| 顧客検索 | `customers.display_name/name_kana` | 個別追加・除外用 |

**禁止（復活させない）**: LTV／売上予測／離脱予測／AI顧客スコア／客単価・利益分析／多店舗比較（PRICE_PLAN §3 Pro・§4 防波堤）。
条件抽出は「事実の絞り込み」であり、スコアリング・ランキング・自動選別ではない。

## 5. AI文案・人による確認・送信の設計原則

1. **AIが勝手に送信しない**（文案は pending。確認済みだけ送信可）
2. **自動大量送信から始めない**（第一段階は条件抽出＋対象確認＋AI文案＋スタッフ確認＋明示送信）
3. 誤送信防止: 送信前確認（対象人数・本文プレビュー）、1回あたり上限、同一顧客への連続送信間隔、送信ログ（誰が・いつ・誰に・何を）、テスト送信（自分のLINEへ）
4. AIへ送らない情報: 氏名・電話・メール・住所・LINE userId・内部ID（既存原則 `SALON_PRIVACY_CONSENT_V1` §4 と同じ）
5. 本文に入れる事実: 店舗名・メニュー名・予約URL・営業時間など公開情報のみ。**値引き・価格の自動生成をしない**（既存キャンペーン案の原則）
6. 将来の高度自動化（自動配信・セグメント自動送信）は**分離**し、別判断

## 6. セキュリティ

| 項目 | 設計 |
|---|---|
| チャネルシークレット／アクセストークン | サーバー側のみ。DBに保存する場合は暗号化（既存のバックアップ暗号化方針と整合）。ログ・UI・エクスポートへ出さない |
| Webhook | **署名検証（X-Line-Signature / HMAC-SHA256）必須**。検証失敗は破棄。冪等化（同一イベント再送対策）。rate limit |
| userId | 個人情報として扱う。テナント境界で厳格に分離。CSV書き出しの対象に含めるかは法務判断 |
| 連携トークン | 短寿命・1回限り。推測不能。連携は**店舗スタッフの確認**後に確定 |
| 送信権限 | 店舗アカウント（共用）で送信可だが、送信操作者名（staff）を必ず記録。Owner PIN 要否は代表判断 |
| 送信上限 | LINE側の月間無料通数／料金に連動する上限をテナント設定に持つ。超過見込み時は送信前に警告 |
| 監査 | 送信ログ・連携ログは append-only。削除は法務方針（保持期間）に従う |
