## 1. 2つの販売導線

Smart Labo Works には、次の2つの導入経路を設けます。どちらから入っても、最終的に利用できるサービス内容は同一です。

### ① 無料相談（相談してから決めたい顧客）

```
無料相談
  ↓
オンラインヒアリング
  ↓
デモ
  ↓
提案
  ↓
契約
  ↓
利用開始
```

### ② 今すぐ申し込む（内容が固まっている顧客・セルフ申し込み）

**2026-07-29 代表決定により、環境を先に作る方式へ正式変更した（下記「販売フローの変更」参照）。**

```
Webサイトで申し込み（会社情報入力）
  ↓
Smart Labo Works 環境作成
  ↓
管理者アカウント作成
  ↓
招待メール送信
  ↓
初回ログイン
  ↓
利用規約への同意
  ↓
payment_required（支払い待ち）
  ↓
Stripe決済
  ↓
active（利用開始）
  ↓
AI初期設定ウィザード
```

### 販売フローの変更（2026-07-29 代表決定）

**旧仕様は廃止した。**

| | 旧仕様（〜SALES-1） | **正式仕様（SALES-2〜）** |
|---|---|---|
| 環境作成のタイミング | 決済成功**後**に会社アカウントを自動作成 | **申込直後に環境を作成**（決済より前） |
| 決済の位置づけ | 契約成立＝決済成功 | 環境作成後、初回ログイン・規約同意を経て決済 |
| 初回ログイン | 決済後 | **決済前**（招待メールから） |
| 支払い前の状態 | 存在しない | **payment_required**（ログイン可・業務機能は不可） |

**変更の要点：** 顧客は支払いの前に自社の環境へログインし、契約内容を画面で確認したうえで決済へ進む。支払いが済むまでは業務機能を使えない状態（`payment_required`）で待機する。

### 契約状態（正式）

```
application_pending  申込を受け付けた（環境未作成）
      ↓
provisioning         環境作成中（会社・管理者・招待の作成）
      ↓
payment_required     環境はできている。支払い待ち
      ↓
active               決済完了。通常利用できる
```

付随する状態として `cancel_scheduled`（解約予約）／`canceled`（解約済み）／`suspended`（停止）を持つ。遷移規則と実装は [15_Stripe_Sales_Billing_Design.md](15_Stripe_Sales_Billing_Design.md) を参照。

### 利用制御（payment_required の間）

**すべてサーバー側で制御する。** 画面の出し分けは利便性のためであり、制御の根拠にはしない。

| | 内容 |
|---|---|
| ログイン | **可能** |
| 利用できる | 契約情報／会社情報／プロフィール／利用規約／支払い画面 |
| 利用できない | **CRM／AI／顧客管理／その他の業務機能** |

**Web上のCTAの役割分担**

| 顧客の状態 | CTA | 遷移先 |
|---|---|---|
| 購入意欲が高い | **今すぐ申し込む**（主CTA） | 申込導線 |
| 内容を相談したい | **無料相談する**（副CTA） | お問い合わせフォーム |
| 機能を確認したい | 機能を見る | 機能ページ |
| 料金を確認したい | 料金を見る | 料金ページ |

**使用しない表現（正式機能として採用していないため）**

無料トライアル／すぐ契約できます／即時利用可能／今なら必ず無料／資料請求／デモ予約

## 2. セルフ申し込み

- セルフ申し込みを**正式に採用**する。
- **支払い方法はクレジットカードのみ**とする（銀行振込・口座振替・コンビニ決済は採用しない）。
- **申込を受け付けた直後に会社環境と管理者アカウントを作成する**（2026-07-29 代表決定。旧仕様の「決済完了後に会社アカウントを自動作成する」は廃止）。
- 管理者は**招待メール**から初回パスワードを設定する。申込時にパスワードは受け取らない。
- 初回ログイン後、**利用規約への同意 → 支払い**の順に進む。
- 決済完了（`active`）後に**AI初期設定ウィザード**へ進む。
- 契約前に**初回決済額と次回決済予定を必ず表示**する。

## 3. 通常料金

**税抜表示を基本とする。**

| 項目 | 金額（税抜） | 備考 |
|---|---|---|
| 初期設定費 | 10,000円 | 申込時に1回 |
| 基本料金 | 20,000円／月 | **管理者1名を含む** |
| 追加アカウント | 3,000円／月・1名 | 2人目以降 |

**利用人数別の月額例（月額のみ・初期設定費を含まない・税抜）**

| 利用人数 | 月額 | 内訳 |
|---|---|---|
| 1人 | 20,000円 | 基本料金のみ |
| 3人 | 26,000円 | 基本料金 ＋ 追加2名 |
| 5人 | 32,000円 | 基本料金 ＋ 追加4名 |

> **金額を変更する場合は、次の4か所をすべて同時に更新すること。**
> ① 本書　② `docs/reviews/tools/check-prices.js` の `CANONICAL`　③ `website-v2/index.html`　④ `website-v2/pricing.html`
> 1か所でも漏れると検証スクリプトが失敗します。

## 4. 課金ルール

| 項目 | 確定内容 |
|---|---|
| 利用開始日 | 申込・**カード決済成功**日 |
| 利用開始のタイミング | 決済成功後、原則としてすぐ利用開始できる |
| 利用開始月 | 基本料金を**日割り** |
| 初回決済 | **利用開始月の日割り分のみ**（SALES-0代表決定・2026-07-28。v1.0の「翌月分もまとめて決済」は廃止） |
| 翌月以降 | **毎月1日に当月分を自動決済**（Stripe。キャンペーン適用時は翌月1日の基本料金部分が0円になるだけで、請求サイクル自体は翌月1日から毎月発生する） |
| 支払い時期 | 月額料金は**前払い** |
| 追加ユーザー（追加アカウント）料金 | 基本料金と**同じ請求サイクル**で扱う |
| 端数処理 | 日割り計算の端数処理は[15_Stripe_Sales_Billing_Design.md](15_Stripe_Sales_Billing_Design.md) 2-3の2案から決済実装前に確定する（代表判断待ち） |
| 事前表示 | 契約前に初回決済額と次回決済予定を表示する |
| **支払い失敗時の猶予（SALES-3R・2026-07-29確定）** | 月次決済に失敗しても**即座には停止しない**。契約は`active`のまま**14日間の猶予**とし、猶予中は業務機能を利用できる（管理者へ支払い警告と更新導線を表示）。猶予期限超過で`suspended`（利用停止）、**さらに30日未解消で`canceled`（解約）**。支払いが確認できた時点で猶予は解除され、`suspended`からも`active`へ復帰できる。猶予は失敗のたびに延長しない（最初の失敗から14日で確定） |

### 会計上の方針

代表意向として、**長期間の前受金が残り続ける複雑な請求方式は避ける。** ただしサービス利用料金は原則前払いとし、毎月1日に当月分を決済することで、請求管理と会計処理を単純化する。

## 5. 創業記念キャンペーン

**正式名称：創業記念キャンペーン**

### 基本特典

| 項目 | 内容 |
|---|---|
| 初期設定費 | 無料 |
| 基本料金 | **1か月分無料** |
| 対象社数 | 先着50社 |
| 条件 | クレジットカード登録必須 |
| 終了条件 | 期間・募集枠に達した場合は終了 |

### 表記ルール（重要）

- Web・資料上では必ず「**基本料金1か月分無料**」と明記する。
- 「初月無料」という表記は**使用しない**。日割りの初月と無料になる月がずれるため、顧客の誤認を招く。
- 「予告なく終了」という表現は使わず、「**募集枠または期間の終了により終了**」と書く。

### 請求例（8月20日利用開始の場合）

| 期間 | 請求 |
|---|---|
| 8月20日〜8月31日 | 日割り料金 |
| 9月分 | 創業記念キャンペーンにより**基本料金無料** |
| 10月1日 | 10月分を通常課金 |
| 以降 | 毎月1日に当月分を自動課金 |

### 無料対象の範囲（SALES-0で確定・2026-07-28）

**無料対象は基本料金のみ。追加ユーザー（追加アカウント）料金は対象外（代表決定・確定）。** Web上でも「基本料金1か月分無料」と表示し、追加ユーザーが無料になると受け取れる表現をしない。無料が適用されるのは**利用開始翌月（最初の満額請求月）の基本料金部分**であり、日割り月には適用しない。

## 6. キャンペーンコード

キャンペーンコードを**正式な販売機能として採用**する。

例：`START2026` / `AUTUMN2026`

### 将来管理する項目

キャンペーン名／キャンペーンコード／割引内容／適用開始日／適用終了日／利用上限／残り枠／対象プラン／クレジットカード必須フラグ／有効・無効／適用企業数

## 7. 紹介コード

紹介コードを**正式な販売機能として採用**する。

例：`AGENT-TOTTORI` / `INSTA01` / `CEO001`

### 目的

- 紹介者・代理店の計測
- Instagram等の流入計測
- 営業担当別の成果計測
- 将来の代理店・紹介制度への対応
- 販売チャネル分析

### 重要な区別

- **紹介コード入力による割引は、現時点では自動付与しない。**
- **キャンペーンコードと紹介コードは、別々の項目・別々の概念として管理する。** 1つの入力欄にまとめない。データモデル上も別カラムとする。

| | キャンペーンコード | 紹介コード |
|---|---|---|
| 目的 | 割引・特典の適用 | 流入元の計測 |
| 金額への影響 | あり | なし（現時点） |
| 入力欄 | 独立 | 独立 |

## 8. AI初期設定ウィザード

決済完了（`active`）後に起動する初期設定の導線。セルフ申し込みで契約した顧客が、営業担当の訪問を待たずに利用開始できる状態をつくることを目的とする。

**本書時点では未実装。** 実装スコープ（設定項目・所要時間・スキップ可否）は SALES-4 で確定する。

## 9. 人間確認原則（AI原則）

販売導線・課金においても、会社全体のAI原則を維持する。

- **AIは提案のみを行う。保存・更新・送信は、利用者が確認して操作する。**
- 申込・決済・契約に関わる操作をAIが自動で確定させることはしない。
- 契約前に初回決済額と次回決済予定を表示し、利用者が確認したうえで確定する。

詳細は [30_AI_Rules.md](30_AI_Rules.md) を参照。
